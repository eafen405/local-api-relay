# 27 — 执行备份门控迁移与显式恢复

**What to build:** 让服务只在完整备份成功后执行前向事务迁移，并让管理员从正常 Operations 或故障恢复入口显式选择、隔离验证和切换本地备份；恢复后的模型路由全部重新进入 Checking，绝不信任备份健康或自动创建空库。

**Blocked by:** 22 — 启动检测并恢复暂不可用模型路由; 25 — 暴露存储降级与 usage 缺口; 26 — 创建并轮换受保护本地备份

**Status:** resolved

- [x] 数据库记录一个整数 schema 版本，二进制携带有序前向迁移，不提供 downgrade migration 或迁移 UI。
- [x] 旧 schema 启动时先创建并验证备份，再在一个事务中完成迁移链和版本更新；验证成功后才能 ready。
- [x] 前置备份、迁移或迁移后验证失败会保留旧数据库并保持 not ready；较新且不支持的 schema 拒绝写入和自动降级。
- [x] 数据库损坏时保留失败文件作为证据、保持 not ready，且不自动恢复、不静默创建空数据库。
- [x] 显式恢复先备份当前数据库，再在隔离候选中验证完整性、应用身份和 schema；新 schema 拒绝，旧 schema 按同一迁移合同处理。
- [x] 只有候选全部通过才切换；切换前失败保持当前数据库，成功后保留配置/秘密/哈希/usage，但所有模型路由重新 Checking 并执行新检测。
- [x] Operations 展示运行/支持 schema、前置备份、迁移/恢复阶段、验证结果、完成时间和可操作 not-ready 原因，不把恢复健康显示为当前健康。
- [x] 自动化和记录式恢复演练覆盖旧/当前/新 schema、损坏库、各阶段故障、成功切换、失败不切换及恢复后健康重建。

## Answer

Implemented backup-gated forward migrations and explicit restore. The database records a single integer schema version (`schema_metadata.version`, now 9); the binary carries the ordered forward-only chain in one transaction with no downgrade migration or migration UI. Opening an older schema first creates and verifies a migration-trigger backup, then runs the whole chain plus the version update in a single transaction and only enters ready after a post-migration integrity check (run inside the transaction so a verification failure rolls the chain back). Pre-backup, migration, or verification failure keeps the old database and blocks ready; a newer-than-supported schema is rejected without any write or downgrade. A corrupted or empty existing database file is preserved byte-identical as evidence, stays not-ready, and is never auto-recovered or silently replaced by an empty database.

Explicit restore selects a managed backup by artifact name, preserves the current database with a restore-trigger backup, stages a private copy of the candidate, and verifies its SQLite integrity, application identity, and schema in isolation; newer schemas are rejected, older schemas upgrade under the same forward-only contract, and only a fully verified candidate is atomically switched into place — any pre-switch failure keeps the current database selected. A successful restore preserves the backup's configuration, upstream secrets, relay-key hashes, and usage history while every model route re-enters Checking and is re-probed, so restored health never influences candidates. Operations shows running/supported schema versions, the migration pre-backup result, the migration/restore phase, verification result, completion time, restore source, and the last-failed stage/reason (the not-ready reason for a failed startup lives in the captured diagnostics, since such a process never serves Operations); the Data security panel offers the explicit restore action with confirmation and busy/result states and exposes no cloud, download, scheduling, or deletion controls.

Process-boundary drills cover old/current/new schema startup, corrupted and empty databases, each gating failure stage, successful switch with health rebuild, and failure-without-switch for newer-schema, corrupted, and migration-failing candidates. Verification passed: `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, `node --check src/web/app.js`, and the full 73-test suite.
