# Map: Define the Lean Local API Relay MVP

## Destination

Produce an implementation-ready MVP specification for a lean local API relay that publishes OpenAI-compatible models, routes each model to the cheapest healthy upstream route, and fails over without inheriting CC Switch's tool-management complexity.

## Notes

- Planning only: this effort resolves decisions and produces the route to a spec; it does not build the product.
- Consult `CONTEXT.md`, `docs/agents/domain.md`, and the local reference source at `tmp/cc-switch/`.
- Use Sub2API's management Web as a functional and information-architecture reference, but specify only the lean subset required by this MVP rather than reproducing its full product surface. The supplied snapshot is at `tmp/sub2api-0.1.173/sub2api-0.1.173`; its embedded server version is `0.1.172`, and it has no commit metadata.
- The relay is a generic provider selected by clients; it does not edit Codex, KimiCode, or other harness configuration.
- One local process serves an OpenAI-compatible API and a local Web management page.
- MVP downstream endpoints: `/v1/models`, `/v1/chat/completions`, and `/v1/responses`.
- MVP upstreams are OpenAI-compatible Chat Completions or Responses providers.
- Each client-visible name is a published model; every route explicitly stores its upstream model name and protocol, with no separate mapping entity. Missing mappings fail fast.
- Harnesses select purpose-specific model names for main work, subagents, and review. The relay does not infer roles from prompts.
- Routes for the same published model are ordered by user-entered cost multiplier, lowest first.
- Failures are isolated per model route, not per entire upstream provider.
- Invalid client requests do not trigger fallback. Transport failures, timeouts, interrupted streams, `429`, and `5xx` responses do.
